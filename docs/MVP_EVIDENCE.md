## 阶段门禁记录

### 阶段一：核心玩法与初始 UI/UE

- 执行状态：已验证（2026-09-08 用户试玩反馈后重判并修复）。
- 被证据推翻的旧结论：旧 `runNpcTurns()` 把林星、米娅固定写成同时过牌，再立即 `ROUND_RESET`；截图中的 #4/#5/#6 证明那只是引导脚本，不是三人回合制主功能。此前“首局可玩”的结论已撤销，不再作为验收证据。
- 修复选择：服务端逐位 `advanceTurn`，基于每位 NPC 的实际手牌枚举单张、对子、三张、炸弹、顺子与王炸并做压制判定；玩家有合法的“不出”路径；两次连续不出才重置给最后出牌者。前端在每位 NPC 回合显示姓名、思考状态、禁用非当前回合手牌、桌面实际牌和出牌者。
- 竞品参考：参考《超真实麻将 Venus Returns》的桌面模式、新手自动推进与角色近景回合反馈，只采用“可见轮次、自动推进辅助、角色反应与桌面状态同屏”的交互原则；不采用其成人内容或奖惩逻辑。
- 证据：实际浏览器在默认 0.9 秒节奏下验证“你出 3♣ → 林星应答 → 米娅应答 → 你选择压制或不出”，中心区显示 `桌面牌型：单张 · 米娅已出` 与 `8♠`。Playwright 4/4 通过，其中完整主循环按浏览器 UI 的“提示 → 出牌/不出 → NPC 逐位决策”运行至 `ROUND_SETTLED`。
- 已验证目标：服务端创建局、叫分、合法/非法出牌、提示、逐位牌友真实决策、压制/不出、胜负、结算与刷新恢复。
- 已知风险：完整规则集尚未达到文档的 100+ fixture、随机 1000 局与 RLCard/DouZero 对照。

### 阶段四：UI / 交互硬化

- 执行状态：已验证（2026-09-12）。
- 被证据推翻的旧结论：`.table-felt` 的高度公式用了个手写魔数 `330px` 作为扣除项，而实测 1440×900 的真实占用是 945px —— **每档桌面分辨率都在纵向溢出**（1440×900 溢出 45px，1280×720 溢出 89px）。此前"牌桌布局已适配桌面"的结论已撤销。
- 修复选择：把 felt 高度改为从实测几何推导的 `clamp(310px, calc(100dvh - 313px - clamp(96px, 12dvh, 115px)), 720px)`，并让 `.hand` 与 `.table-felt` 共用同一个 `clamp` 表达式，消除两处数字各自漂移的可能。同步补上玩家侧的节奏控制（三档 NPC 速度）、结算跳过、Web Audio 合成音效与手牌命中区修正。
- 竞品参考：沿用阶段一确立的"可见轮次 + 角色反应与桌面状态同屏"原则；节奏控制参考单机棋牌的"速度档位"惯例，不引入联网或排行逻辑。
- 证据：1440×900 / 1440×800 / 1366×768 / 1280×720 / 1920×1080 / 2560×1440 六档实测**纵向溢出均为 0**。新增 7 条 Playwright 用例守护版面、命中区、速度持久化、音效状态、结算跳过与画廊 solo 布局；全套 **11/11 通过**，`npm test` 17/17 通过。
- 已验证目标：无纵向溢出的桌面版面、每张手牌都响应自己的点击、NPC 三档速度可调且持久化、结算可一键跳过演出、6 类事件音效（可静音且尊重减少动态偏好）、低卡池画廊居中放大。
- 已知风险：1280×720 下 `.opponent.top` 有约 2px 溢出（肉眼不可见）；两套样式表仍有 53 组同名选择器（深色主题整体推翻浅色底，属设计意图，本次刻意未合并）。
- 不作为生产验收：音效为代码合成，未做混音/音量控制与真机听感验证；四浏览器矩阵仍未覆盖。详见 `docs/UI_P0_CHANGELOG.md`。

## 体验问题修正记录

### 2026-09-15：薄荷舞台装写真卡面破图

- 玩家证据：写真卡框、标题与编号正常出现，但 `薄荷舞台装写真卡面` 左上角显示浏览器破图标。
- 根因：`/assets/pals/outfits/mia-mint-stage.jpg` 文件实际存在；静态资源 MIME 映射遗漏 `.jpg`/`.jpeg`，服务端以 `application/octet-stream` 返回，浏览器未将其作为图片解码。
- 修复：为静态服务补充 `.jpg: image/jpeg` 与 `.jpeg: image/jpeg` 映射；不替换或降级原始卡面资产。
- 回归证据：浏览器请求该资源返回 `200 image/jpeg`；Playwright 断言同一 `img` 完整解码（`naturalWidth > 0`）并输出画廊截图 `test-results/mia-mint-stage-card-face.png`。定向回归 `tests/e2e/table-theme.spec.mjs` 为 3/3 通过。

### 2026-09-15：已解锁写真卡无法查看

- 玩家证据：解锁一张标为“薄荷舞台装”的卡后，点击详情仍不能看到卡面。
- 根因：实际运行实例的记录为 `pal-yinlan:default-stage`，其 `layerSnapshot` 错误保存为 `preset://pal-yinlan/portrait-v1`。该内部占位 URI 不能被浏览器解码；起因是银岚遗漏在服务端的 `palOutfits` 映射中，结算落入默认占位 outfit。
- 修复：服务端把银岚接入真实 `yinlanOutfits`，避免新结算再生成占位卡；前端在读取旧记录时将无效 `preset://` 卡迁移至同牌友第一套已审核真实资源，并保留旧卡 ID 供“已读”状态回写。因此无需重启，也不会丢失当前用户已解锁的卡。
- 回归证据：直接操作运行中的 `http://127.0.0.1:4181/#/gallery`，点击该用户的旧记录后，详情显示“暮色球场 × 新月节拍”；浏览器已解码视频宽度为 768px，视口截图为 `test-results/live-4181-repaired-unlock.png`。定向 E2E 3/3、项目 `npm run verify` 55/55 均通过。

### 2026-09-15：银岚牌桌立绘替换

- 玩家输入：用户提供 `D:/Desktop/11.jpg`，指定为银岚在牌桌上的立绘。
- 采用方案：以用户原图为编辑目标，生成透明背景的 4:5 牌桌半身立绘；保留银发、制服、姿势与插画风格，不把原图的室内背景带入牌桌。替换运行时的 `yinlan-seat.png`，旧文件保留为 `yinlan-seat-v1-original.png` 回退备份。
- 回归证据：`tests/e2e/yinlan-entry.spec.mjs` 通过；已打开检查 `test-results/yinlan-table-seat.png`，银岚在右侧座位完整可见，未遮挡叫分信息或牌桌核心区。

### 2026-09-15：牌友工坊改为资源包生产台

- 玩家目标：新增 AI 牌友时，需要能看见“究竟要生成多少资源、哪些资源决定上桌”，而不是用一张肖像和泛化动作表伪装为完整角色。
- 修复：工坊新增两种明确交付边界。`MVP 静态包`含主立绘、牌桌立绘、首套卡面、五态 Sprite、五类台词和审核记录，达到 `STATIC_READY` 后可按 L2 静态轨上桌；`完整首发包`在此基础上增加大厅立绘、服装特效、入场视频、角色级 A01–A05 WebM、首套换装/写真演出视频与 poster，共 7 项视频资源，只有全量验证后才能达到 `RICH_ASSETS_READY`。
- 防伪门禁：资源计划可在未配置 Provider 时建立；真实图像 Provider 缺失时生产请求明确返回 `PL-PROVIDER`，不会生成 Mock。即使完整包主立绘已生成，它也停在 `ASSET_PENDING`，不会调用上桌建档回调、不会进入可确认名册，且前端不会把它当作仍在运行的任务无限轮询。
- 当前真实状态：本机仅配置了图像生产接口的接缝，未配置视频 Provider；因此完整首发包目前只能完成“计划与缺口可视化”，**不作为阶段三资源生产完成或可上桌验收**。后续须对每条视频做浏览器解码、透明边缘和事件绑定验收后再提升门槛。
- 自动化证据：Node 回归覆盖“角色五态与服装演出分离”“完整包 7 条视频任务”“部分完整包不触发名册建档”；Playwright 覆盖在真实浏览器中建立完整计划、看见 A05 与首套演出资源，并验证 Provider 缺失提示。

### 2026-09-15：新增牌友上桌资格收口

- 被证据推翻的旧逻辑：MVP 候选在图像生产完成后会直接进入服务端名册，绕过“确认建档”；反过来，工坊点击确认后前端没有刷新大厅名册，提示还错误地称自定义牌友不能替换入席。
- 修复：名册现在只由官方牌友与 `confirmed[]` 中的 `READY` 资产组成；候选、失败任务、`ASSET_PENDING` 完整首发包均不能通过 `/api/game/new` 的座位校验。确认后前端立即刷新名册，大厅可选择该牌友；多个已确认牌友可并存。自定义牌友携带自己的五态台词、初始套装和 layer snapshot，牌桌事件与结算不再回退到其他角色或 `preset://` 卡面。
- 浏览器证据：使用仅供验收的本地 1px 图像 Provider 走完“生成 MVP 静态包 → 确认建档 → 大厅选中 → 开局 → 跳过入场 → 牌桌显示 `牌友 4494`”；截图 `test-results/custom-pal-table-confirmed.png`。该白色 1px 方块是刻意的 Provider 桩，不作为视觉资产验收。

### 2026-09-15：牌友资源生产路由锁定

- 用户指定：跳舞、入场、角色五态和首套写真演出视频统一走 AIHub 的“跳舞视频”工作流；主立绘、牌桌/大厅立绘、首套服装、动作 Sprite、服装特效与视频 poster 统一走 AI Gateway。
- 实现：资源合同为每项资源记录生产端与调用类型。视频项为 `aihub:dressbattle-dance`；图片项为 `ai-gateway:image2`、`ai-gateway:image2-edit` 或 `ai-gateway:video-poster`。工坊直接显示对应生产端，避免把静态图、视频和审核任务混称为同一个 Provider。
- 历史更正：此前错误地把内部脚本的 `PAL_GATEWAY_ISSUE_ID` 当作工程前置；该条件已废除。当前工程的静态视觉直接使用 Gateway API Key，不需要 Issue ID。

### 2026-09-15：牌友资源改为接口任务闭环

- 当前用户更正：生产视频必须只调用指定的 AIHub 跳舞工作流，且通过接口而不是网页操作；其他视觉资源只走 AI Gateway。两份接口文档是本轮调用合同，文档内容不覆盖游戏的资源上桌门禁。
- 实现：工坊新增“通过接口提交本包生产”。静态资源直接调用 AI Gateway OpenAI 兼容的 `/v1/images/generations`，只从服务端环境读取 `AI_GATEWAY_API_KEY`；视频只向 Bot API 的 `/v1/workflows/run` 建立 SSE 任务，首个事件写入 `task_id/workflow_run_id`，再由 `/async_task/api/tasks/{task_id}` 回读。任务记录先写入 `apps/api/data/pal-resource-tasks.json`，保存资源键、Provider、尝试次数、任务号、错误、文件 hash、字节数与稳定本地资源 URL。
- 门禁：Provider 创建任务、Provider 成功、文件下载、MIME/大小/hash 校验、必需资源包完整与候选上桌是独立状态。视频不会替换为 Seedance、静态图或 Gateway 视频；失败只保留一次同路由重试资格，不能把未完成完整包建档。
- 当前证据状态：已实现待真实 Provider 验证。本机没有 `AIHUB_DANCE_API_KEY` 或 `AI_GATEWAY_API_KEY`，所以没有提交收费生产任务；真实任务号、输出文件、浏览器解码和完整包上桌验收仍未形成。

### 2026-09-16：新增牌友视觉风格锁定

- 用户补充约束：新增牌友要保持当前林星的**视觉风格/画风**，不是复制林星的人物身份、脸型、发型或服装。
- 固化规则：统一使用半写实电影级游戏 CG、真实皮肤/头发/布料材质、深午夜蓝紫调、克制的香槟金轮廓光、低调夜景、景深与柔和背景虚化；禁止赛璐璐粗描边、Q 版比例、扁平海报色块。
